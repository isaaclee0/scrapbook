# Cache worker reliability deployment — 13 October 2026

## Result

Released **2.6.1**, source commit `6badd8b48`, to the existing `scravbookv2`
stack on `flatwhite`. Web and worker use the same new image. MariaDB and Redis
were not recreated. The image was published for `linux/amd64` and `linux/arm64`
with tags `v2.6.1`, `2.6.1`, and `latest`.

Registry manifest digest:
`sha256:706d2d0383a5144c7198e45beb5603f0fe8165442bedec3b0b398f666a1bf9dd`.

## Root causes

- Worker inherited the image's HTTP health check but does not run an HTTP server.
- Counting/selection used `retry_count < 3 OR cooldown elapsed`, whereas the
  downloader refused retries at 3 regardless of cooldown. Selection also admitted
  recent failures whose cooldown had not elapsed.
- Selection joined failure history through `pins.cached_image_id`, but failure
  writes used URL/quality without necessarily attaching that record to the pin.
  Production had 128 exhausted references with a NULL pin cache ID.
- The LIMIT repeatedly selected exhausted items ahead of eligible work. Default
  idle settings never applied the intended no-progress backoff.
- Queue-count changes were reported as approximate successes, even though a
  smaller eligible queue can mean failures entering cooldown.

## Changes

- Shared SQL eligibility and DB clock for counting, selection and downloading,
  joined by original URL/quality and filtered before LIMIT.
- Three-failure budget retained; cooldown after failures is exponential. Existing
  exhausted records are excluded without resetting their history.
- Nullable `failure_kind` and `last_error` fields distinguish retryable failures
  from unsupported content and permanent HTTP responses. Existing HTML thumbnail
  scraping and direct-video frame extraction remain the supported workflows.
- MariaDB advisory locks serialize each URL/quality across web and worker
  processes. Success upserts survive overlapping legacy failures. Missing cache
  files retire stale metadata without reopening an exhausted retry budget.
- Actual batch results, default 300-second empty/no-success backoff, and connection
  cleanup. HTTP response streams are closed on both success and failure.
- Activity heartbeat updated by loop work, download chunks, task completions and
  intentional sleeps. No independent heartbeat thread can mask a stuck batch.
  The health probe checks heartbeat age and process existence.
- Both maintained compose files contain the worker-specific health check.

## Verification

- **90 tests passed** under the production image's Python 3.11/dependencies,
  including five tests against disposable MariaDB 11.6.2 and a local fixture HTTP
  server. Coverage includes successful WebP persistence/attachment, cooldowns,
  exhausted/unlinked starvation, terminal content, transient failures, duplicate
  tasks, independent service connections, and success-upsert IDs.
- Additive migration ran twice successfully in a disposable database and retained
  an existing exhausted row, including its retry count and filename.
- Disposable Docker worker was healthy during idle, became unhealthy when its
  process was paused, then recovered after resuming.
- Production worker's first batch processed **44 eligible references**, reporting
  **0 cached, 44 failed/skipped, 0 eligible remaining**. Failures were 20 unsupported,
  7 permanent HTTP failures, and 17 retryable responses (403/429).
- Remaining uncached pin references: **331 exhausted**, **27 terminal**, and
  **13 cooling down**. No new production cache files were generated by that batch;
  these URLs supplied unavailable/unsupported content. Successful download and
  cache-file creation were verified by the integration tests, not inferred from
  a falling queue count.
- Public site returned HTTP 200 and `/health` returned `{"status":"ok"}` after
  rollout. Existing cached bytes were verified directly (valid image, 79,620 bytes
  matching metadata). An unauthenticated cached-image request returned 403, as
  access requires authentication; authenticated end-to-end delivery was not tested.
- Counts remained unchanged across rollout: 146,909 pins; 146,903 gallery images;
  140,819 cache records; 668 boards; 1,028 sections. Hash comparison confirmed all
  **299 pre-existing exhausted URL records** retained their exact retry counts.
- Production remained healthy through a full 300-second idle interval, then logged
  `No eligible images; sleeping 300.0s`. Worker heartbeat age was under 5 seconds;
  web and worker restart counts were zero. Running worker/service source hashes
  matched the released source. No web HTTP 5xx responses appeared after recovery.
- Named cache/database/Redis volumes remained unchanged. No pins, image files,
  database records, or production volumes were deleted, and no global retry reset
  was performed.

## Deployment details and remaining operational issues

Portainer's maintained source is `/data/compose/31/docker-compose.yml` in the
`portainer_data` volume. It is an editor-managed stack, without a Git checkout.
Only its worker healthcheck block was changed; parsed comparison confirmed all
other compose settings were identical. Portainer's saved stack variables remain
separate and unchanged.

The first direct Compose invocation omitted those separately stored variables.
Web was promptly recreated with the exact saved stack environment; DB password,
JWT secret and email API settings were checked for equality without displaying
values. Web was healthy before the worker rollout continued. Future updates
should use Portainer's stack update flow, or explicitly supply its saved variables
when invoking Compose. A compose file alone is insufficient for this stack.

Compose backup in Portainer's volume:
`/data/compose/31/docker-compose.yml.before-cache-worker-2.6.1-20261013T080132Z`.
The previous server image is retained as
`staugustine1/scrapbook:rollback-2.6.0`. Rolling back code requires restoring the
previous worker health configuration too; the additive columns may remain.

The GitHub Actions release workflow still fails because the `DOCKER_PASSWORD`
secret is missing. The Docker cloud builder also reported zero concurrency
allowance. Release images were successfully built and pushed using the existing
local multi-architecture builder (`cloud-builder`) following the documented
buildx release process. These CI/account configuration issues are separate from
the deployed worker fix.
